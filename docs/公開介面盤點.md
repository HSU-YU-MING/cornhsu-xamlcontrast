## 1. 範圍與名詞

| 名詞 | 意思 |
|---|---|
| 契約面 | 使用者的腳本、CI、repo 檔案會依賴其形狀的介面。1.0 後破壞即 major |
| 非契約面 | 給人看的輸出（console、Markdown）、未發佈的 C# 型別。可隨版調整 |
| root | CLI 的位置參數 `<project-root>`，稽核範圍與 config 的所在目錄 |
| CWD | 執行 `xamlcontrast` 時的工作目錄；所有輸出路徑與 baseline 預設路徑都相對於它 |

本套件在 0.x 期間的版號慣例（由 CHANGELOG 歸納）：破壞性變更跳 minor（例：v0.6.0 拿掉
ok/decorative 的 `symmetry`），契約面的新增跳 minor（例：v0.3.0 `--sarif`、v0.5.0 `--md`），
修正、文件與非契約輸出的調整跳 patch（例：v0.5.1 只改文件；v0.6.1 新增 console 求救提示並修文件）。
1.0 之後照 Parity 的規則：任一凍結面破壞 → major；只增 → minor；修正 → patch。

## 2. CLI

### 2.1 指令形狀

```
xamlcontrast <project-root> [options]
```

單一指令、沒有子指令。執行檔名與 `ToolCommandName` 都是 `xamlcontrast`
（`src/XamlContrast.Cli/XamlContrast.Cli.csproj:7`、`:11`），套件 ID `Cornhsu.XamlContrast`（`:12`）。
CLI 組件用 top-level statements，**沒有任何 exported type**（反射實查）。

**執行環境**：目標框架只有 `net10.0`（`XamlContrast.Cli.csproj:5`），沒有設 `RollForward`，所以使用者的機器或 CI
必須有 .NET 10 runtime——預設的 roll-forward 政策（`Minor`）不會跨 major 改跑在較新的 runtime 上。TFM 不在官方凍結定義內，
但它直接決定「裝不裝得起來、跑不跑得動」：哪天只出 `net11.0`，只裝了 .NET 10 的既有 workflow 就用不了新版。建議 1.0 時明文宣告支援的
runtime 政策（例如設 `RollForward=Major`，或多目標），並把換 TFM 視為需要在 CHANGELOG 標明的變更。

### 2.3 解析規則（實測確認）

- **順序無關、由左到右一次掃過**；同一旗標重複時後者勝。第一個不以 `-` 開頭的字是 root（`Program.cs:73`）——
  所以以 `-` 開頭的目錄名不能當 root。
- `-h`／`--help`／`--version` 是**掃到就結束**：`--help --bogus` → exit 0；`--bogus --help` → exit 2（實測）。
- **`--baseline`／`--write-baseline` 的值可省略**：下一個字不以 `-` 開頭就被當成路徑（`Program.cs:57`、`:61`）。
  因此 `xamlcontrast --baseline src/MyApp` 會把 `src/MyApp` 當 baseline 路徑、root 落空 → 印 usage、exit 2，
  而且 stderr 沒有任何說明（實測）。
- **反方向的問題：`--json`／`--sarif`／`--md` 的值必填，但不檢查是否以 `-` 開頭**（`Program.cs:43-54` 只檢查
  `i + 1 >= args.Length`），所以會吞掉下一個旗標並寫出同名檔：`--json --show-ok` 寫出一個檔名叫 `--show-ok` 的 JSON，
  `--show-ok` 本身被靜默吃掉。實跑 `xamlcontrast samples/demo --json --sarif`：exit 1、stdout 印 `json written: --sarif`、
  CWD 多出一個名為 `--sarif` 的檔，沒有任何警告。2.2 的「缺值 → exit 2」只在旗標剛好是最後一個字時成立。
- **互斥關係：程式沒有強制任何互斥。** 實際行為：
  - `--write-baseline` 與 `--baseline` 同時給 → `--write-baseline` 勝，`--baseline` 被靜默忽略（`Program.cs:206` 先判）。
  - `--json`／`--sarif`／`--md` 可任意組合，也可與兩種 baseline 模式並用。
  - `--show-ok`／`--show-unresolved` 只影響 console，與其他旗標無關。
- **與 config 的優先序**（`Program.cs:112-117`）：
  - `failOn`、`strictPalette`：**旗標只能加嚴**（`flag || config`）。`--fail-on fail` 無法把 config 的 `"warn"` 放寬。
  - `minCoverage`：**旗標兩個方向都能覆寫** config（`minCoverage ?? config.MinCoverage`）。這是唯一可以放寬的。
- **路徑基準**：`--json`／`--sarif`／`--md`／`--baseline`／`--write-baseline` 都相對 CWD；config 檔永遠是
  `<root>/xamlcontrast.config.json`（`Config.cs:89`），沒有 `--config` 旗標。寫檔不代建目錄（`Program.cs:149`）。
- 寫出檔案後在 stdout 印 `<label> written: <path>`（`Program.cs:155`）；`--write-baseline` 另附 `(<N> known failure pair(s))`。

### 4.7 凍結判讀與命名／形狀建議（只建議，不改）

**判讀：未達凍結。** 形狀本身已穩定兩個多月，但有一批命名與型別問題，**改任何一項都是破壞性的**，

1. **同名不同物**：

4. **沒有 outputs**：建議至少 `exit-code`、`report-json`（路徑）、`fail-count`。只增。
5. **同一個 workflow run 用兩次會互撞**（依 upload-artifact v4 起「同名 artifact 不可重複上傳」的規則推定，未在 GitHub 上實測）：
   artifact 名稱固定、PR 留言標記固定。建議加 `report-name` 之類的 input，或從 `root` 推導。
6. 內部 action 以 major tag 引用；release.yml 已對 `NuGet/login` 做 SHA 釘選，Action 本身是否比照可一併考慮（不影響介面）。

## 9. baseline 檔

### 9.1 寫出格式（`Baseline.Write`，`Baseline.cs:42-53`）

```json
{
  "comment": "XamlContrast baseline \u2014 known debt; may only shrink",
  "entries": [
    { "file": "MainWindow.xaml", "element": "TextBlock", "fg": "White", "bg": "{Surface}", "count": 1, "worst": 1 }
  ]
}
```

| 欄位 | 型別 | 說明 | 來源 |
|---|---|---|---|
| `comment` | string | 固定字串；讀取時忽略 | `Baseline.cs:52` |
| `entries` | array | **必填**；只收 `category == fail` 的 findings，依 `file`、`element`（ordinal）排序 | `Baseline.cs:44-51` |
| `entries[].file` | string | 同 `findings[].file` | `Baseline.cs:17` |
| `entries[].element` | string | 同 `findings[].element` | 同上 |
| `entries[].fg` | string | 同 `findings[].fg`（原始文字） | 同上 |
| `entries[].bg` | string | 同 `findings[].bg`（正規化） | 同上 |
| `entries[].count` | integer | 同鍵的處數 | 同上 |
| `entries[].worst` | number | 同鍵所有處中最差的 `min(ratioDark, ratioLight)` | 同上、`:49` |

序列化：camelCase、縮排、非 ASCII 跳脫（上例的 `\u2014` 就是 `—`，照實際輸出抄錄）、檔尾無換行（`Baseline.cs:28-33`）。

### 9.2 讀取與比對（`Baseline.Compare`，`Baseline.cs:55-105`，實測確認）

- **鍵** = `file|element|fg|bg`，刻意不含行號（`Baseline.cs:35`；`CLAUDE.md`「baseline 的鍵」）。同鍵重複的 entry 後者勝。
- `entries` 裡每筆的欄位名不分大小寫（`File`、`Count` 也讀得進）；但頂層的 `entries` 用
  `JsonDocument.GetProperty("entries")` 讀，**大小寫敏感**——整份 PascalCase 的檔（頂層寫成 `Entries`）
  會 exit 2（`baseline is not valid (…): The given key was not present in the dictionary.`，`Baseline.cs:59`；
  欄位走 `:61` 的 `Deserialize<Entry>`，那裡才有 `PropertyNameCaseInsensitive`）。未知屬性忽略；`comment` 可省。
- 缺 `entries` → 例外 → CLI exit 2；`entries: null`、元素為 `null`、型別錯 → exit 2。
- **缺欄位靜默補預設**：缺 `count` → 0（等於每筆都算惡化，會吵）；缺 `worst` → 0（等於**色盤漂移檢查靜默失效**）。
- 判定：
  - 目前有、baseline 沒有的鍵 → NEW（逐處列出）。
  - 目前處數 > `count` → WORSENED。
  - 目前最差比值 < `worst − 0.01` → WORSENED（色盤漂移；容差 0.01）。
  - 其餘 → `knownDebt += 目前處數`。
  - baseline 有、目前完全沒有的鍵 → `paidDebt += count`（處數，不是鍵數）。

### 9.3 變動頻率與凍結判讀

- `Entry(File, Element, Fg, Bg, Count, Worst)` 與 `Write` 的輸出自 v0.1.0 **逐字未變**（比對 v0.1.0 與 HEAD）；
  鍵的三個組成字串（`element`／`fg`／`bg` 的格式）也自 v0.1.0 未變。與壓抑註解語法（第 10 節）並列為最穩的面。
- 但鍵的**內容**受稽核語意影響：解析規則一改（例如 v0.6.0 的規則 17 讓某些 `bg` 從祖先底換成兄弟背板），
  同一個問題的鍵就變了，使用者會看到假性 NEW。這不是格式問題，是「鍵的穩定性承諾」問題。
- **判讀：格式可凍結，建議先補四件事**：
  1. 加 `version`（或 `schemaVersion`）欄位——只增，但沒有它就無法在 1.x 演進格式。
  2. 讀取時缺必要欄位（`count`、`worst`）應報錯（exit 2）而不是補 0。（fix/product-bugs：先改為點名警告；exit 2 待決定。）
  3. 明文寫下鍵的穩定性承諾：哪些變更會改變鍵（`fg` 從 `StaticResource` 改 `DynamicResource`、加 Opacity 都會換鍵；
     **執行的 locale 不同也會**——`fg` 的 ` ×<op>` 依 CurrentCulture 格式化（4.4），en-US 機器寫出的 baseline 拿到
     de-DE 的 CI 上比對，每一筆帶 Opacity 的 fail 都會變成 NEW 加 paid off、CI 紅燈。這一項應先修成 InvariantCulture，
     而不是寫進承諾）、稽核語意改變導致換鍵時是否算 major、遷移方式（重跑 `--write-baseline`）。
  4. 讀取規則要一致（9.2）：頂層 `entries` 大小寫敏感、每筆的欄位名不分大小寫——兩者的大小寫政策擇一。（fix/product-bugs：頂層改為不分大小寫。）
- 行為面（非格式）的兩點備忘：ratchet 不會自動收緊——同鍵從 3 處修到 1 處，之後又回到 3 處仍會通過，除非重寫 baseline；
  `paid off` 只計整個鍵消失的處數，部分償還不計。

## 10. 原始檔層面的約定：稽核範圍與壓抑註解

1.0 之後改動一樣會打壞人——前者讓同一個 repo 的稽核範圍悄悄變大或變小，後者讓既有的壓抑靜默失效。

### 10.2 壓抑註解 `<!-- xamlcontrast-ignore: 理由 -->`

規畫書 4.6 的導入機制，CHANGELOG 0.1.0 列為對外功能。使用者把它寫進**自己的 XAML 原始檔**，所以語法是契約：
語法一改，所有既有的壓抑靜默失效——被壓的配對重新出現、CI 由綠轉紅。

| 項目 | 實際行為 | 來源 |
|---|---|---|
| 語法 | 註解內文整段符合 `^\s*xamlcontrast-ignore(?:\s*:\s*(?<reason>.*\S))?\s*$`：**大小寫敏感**；錨定在註解開頭（`TODO: xamlcontrast-ignore: …` 不算）；關鍵字前後、冒號兩側的空白都容忍，冒號後不必空白；**理由必須在同一行**（沒開 Singleline／Multiline，`.` 不吃換行） | `Auditor.cs:91-92` |
| 位置 | 只認元素**緊鄰的前一個非空白節點**；中間隔了另一個註解或元素就不算。一個註解只管一個元素 | `Auditor.cs:99-104` |
| 作用範圍（樹走訪） | 下一個元素**連同整個子樹**：子樹內每一組解析成功的配對照樣計入 `pairs`，另計入 `suppressed`、不進 `findings`。⚠ 子樹內**無法解析**的配對不受影響，照常計入 `unresolved`（實測） | `Auditor.cs:246-248`、`:403`、`:443` |
| 作用範圍（Style 定義處） | 緊鄰 `<Style>` 的 ignore 壓掉該 Style 定義處（WalkStyles）的配對。⚠ 定義處**只看緊鄰 `<Style>` 的那個註解**：容器上的 ignore 會壓掉容器內「元素 × Style 鏈」的配對，但**壓不到**容器 `Resources` 裡 Style 定義處的配對（實測：ignore 加在含 `Grid.Resources` Style 的 Grid 上，Style 那組照報） | `Auditor.cs:560`、`:673` |
| 理由 | `ignore.requireReason`（預設 `true`）時理由必填：`<!-- xamlcontrast-ignore -->` → 不壓、記入 `invalidIgnores`。設成 `false` 時沒理由也生效（仍計入 `suppressed`） | `Auditor.cs:107-112`；`Config.cs:72` |
| 寫錯的變體 | 大小寫不同（`XamlContrast-Ignore: …`）、冒號後沒有理由（`xamlcontrast-ignore:`，或冒號後只有空白）、漏冒號（`xamlcontrast-ignore 浮水印`）、**理由寫成兩行**（`xamlcontrast-ignore: watermark text,` 換行接 `intentionally faint`——理由本身合法，只是換了行）都**整段不符合**：不壓，**也不進 `invalidIgnores`**，沒有任何訊息（實測皆 `suppressed 0`、`invalidIgnores` 為空）。配對照報，所以不會造成虛假的通過，但使用者看不出自己的註解沒生效 | `Auditor.cs:105-106` |
| `invalidIgnores` 訊息 | `"<file>:<line>: xamlcontrast-ignore without a reason is invalid (not suppressed)"`；`<file>` 為 root 相對、正斜線，`<line>` 是**註解**所在行 | `Auditor.cs:109-110` |
| 揭露 | console：`suppressed N pair(s) via xamlcontrast-ignore comments` 與每一筆 invalid；JSON：`summary.suppressed`、`summary.invalidIgnores`（4.2）；Markdown：`Not evaluated` 行的 `N suppressed via xamlcontrast-ignore` 與 invalid 提示 | `Report.cs:154`、`:305-306`、`:443`、`:454` |

### 10.3 變動頻率與凍結判讀

- 壓抑註解的正則、「緊鄰前一個節點」與 `invalidIgnores` 訊息自 v0.1.0 逐字未變（比對 v0.1.0 與 HEAD 的 `Auditor.cs`）；

### 15.1 `--push`（實驗性，未發佈：CHANGELOG 的 Unreleased）

把 `--json` 寫好的報告原樣上傳到 Parity.Server 的團隊儀表板，**不稽核**。**不在 1.x 凍結面內**：儀表板公開上線之前，
下表每一項（旗標、環境變數、push 模式的退出碼）與伺服器協定都可以在 minor 改；上線後旗標併入第 1 面、退出碼併入第 2 面。
用旗標不用子指令：2.1 的單一指令形狀下，`xamlcontrast push` 是「稽核名叫 push 的目錄」，子指令會破壞凍結。Action 不加 input
（一加就凍結），README 改教使用者在 action 之後自己接一步 `xamlcontrast --push "$RUNNER_TEMP/xamlcontrast-report.json"`。

| 旗標／環境變數 | 參數 | 預設 | 作用 | 錯誤用法 → 退出碼與訊息（stderr） | 來源 |
|---|---|---|---|---|---|
| `--push <path>` | 檔案路徑（必填、不得以 `-` 開頭，同 `--json`） | — | 報告原樣 `POST {server}/api/runs` | 缺值 → `--push takes a file path`；與 root、`--` 或任何稽核旗標並用 → `--push uploads an existing report and does not audit — drop …`；檔案不存在 → `report not found: …`；不是這個版本 `schemaVersion` 的 XamlContrast 報告（Parity 的 `report.json`、較新或 0.x 的格式、缺 `summary`／`findings`）→ 點名原因。全部 exit 2、不送 | `Program.cs`、`Push.cs` |
| `--server <url>` | 絕對 `http`／`https` 網址 | `XAMLCONTRAST_SERVER` | 儀表板位址 | 都沒有 → `missing server: …`；不合法 → `--server must be an absolute http or https URL`（來自環境變數時點名 `XAMLCONTRAST_SERVER`）；沒有 `--push` → `--server only works with --push`。exit 2 | 同上 |
| `--commit <sha>` | 非空、不得以 `-` 開頭 | `GITHUB_SHA` | `X-Parity-Commit` | 缺值 → `--commit takes a commit SHA`；沒有 `--push` → exit 2 | 同上 |
| `--branch <name>` | 非空、不得以 `-` 開頭 | `GITHUB_HEAD_REF`，再 `GITHUB_REF_NAME`（空字串當沒設） | `X-Parity-Branch`；非 ASCII 的值不送、stderr 註明 | 缺值 → `--branch takes a branch name`；沒有 `--push` → exit 2 | 同上 |
| `XAMLCONTRAST_TOKEN` | 環境變數（**刻意沒有旗標**） | — | `Authorization: Bearer <token>` | 沒有或只有空白 → `missing token: …`；中間有空白／控制字元 → 點名；exit 2、不送 | `Push.cs` |

- **退出碼**：0 送出（2xx）；2 其他一切（用法、token、檔案、連不上、逾時 60 秒、非 2xx）。不會是 1 或 3（稽核的判定）。
- **其他標頭**：`X-Parity-Tool: xamlcontrast`（一律）、`X-Parity-Triggered-By`（`GITHUB_ACTOR`）、
  `X-Parity-Repo-Url`（`GITHUB_SERVER_URL` 與 `GITHUB_REPOSITORY` 都有時）、`X-Parity-Gate`（報告的 `exitCode`：0 → `pass`，1／3 → `fail`，`null` → 不帶）。
- **回應**：201 印 `pushed:`／`project`／`result`／`view`；`GITHUB_STEP_SUMMARY` 有設時附加一行儀表板連結（圖示先看伺服器的 `gateFailed`，
  沒有才看報告的 `exitCode`）。非 2xx 印 `server returned <code> <reason>: <error>`，401／413 另附提示；3xx 不跟、印 `Location`。
  伺服器回的文字一律經 `Report.ConsoleSafe`。
